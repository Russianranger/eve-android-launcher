## Optimization implications

Keep Mesa 26.2.4 and linear presentation enabled as the user's improved base.
Preserve full color, input, correctness fences, data and shader caches. SHM
and the separate CPU Canvas surface remain independently neutral experiments,
so another trial of those unchanged paths is lower priority.

Native render/completion/readback phases need better bounded attribution;
client worker/synchronization overhead is more promising than reducing idle
shader-worker counts. Xvnc/RFB/Android upload still moves substantial full-color
data during camera activity. The mostly idle server is not a measured FPS
bottleneck in this capture. Keep the next three candidates independently switchable and test their batch on
the improved base so regressions remain attributable.

One candidate reduces disposable diagnostic-write work without changing
sampling or enforcement. Its optional `lean_writes` mode caches each completed
sample's JSON once, tracks its exact encoded size, and reserializes only the
small report header while evicting old samples. It preserves atomic replacement,
the 256 KiB file limit, 120-sample cap and all process/cache/hardware sampling
intervals. Only periodic starting/running performance reports omit `fsync`;
stopping and final stopped/failed reports still request it. Ownership journals,
world data, health and memory enforcement are unaffected. A sudden process or
device loss can lose the newest disposable report; this is not durable gameplay
state. `diagnosticWritePolicy` records requested/effective policy and encoding/
write/fsync-request counters; those requests are not proof of storage completion.

A five-repeat host benchmark replayed 120 captured samples through the original
0.1.20 writer and the lean writer, including temporary-file atomic replacement.
`fsync` was mocked in both paths to isolate CPU work. Both retained 40 samples
and performed 80 byte evictions. Median CPU time fell from 351.605 ms to
55.990 ms, while bytes passed through JSON encoding fell from 47,220,744 to
1,510,217 (96.8% less encoding work). Lean made more, much smaller JSON calls:
320 versus 200. This saves only about 2.46 ms host CPU per five-second sample;
it is a modest background-overhead candidate, not evidence of an FPS gain.
Avoided periodic sync cost and physical benefit require Thor testing.
