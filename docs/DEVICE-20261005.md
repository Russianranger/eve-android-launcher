# October 5 Thor station measurements

The four supplied exports use launcher 0.1.13, Wine 10.13/FEX 2510,
native ARM64EC DXVK 2.4.1, Turnip 26.0.0 and 1280×720. The user held the camera
static and observed initially slow performance, subsequent warm-up, temperature
rise and a small memory increase in every run. The baseline closed completely.

## Crash evidence

The baseline's newest Android ApplicationExitInfo records reason 3 (LOW_MEMORY)
at 2026-10-05 10:12:23.408 UTC, immediately after the final running sample.
Launcher PSS was 107,892 KiB and RSS 214,000 KiB. Both runtime supervisors
disappeared without normal cleanup; the display connection reset. No Java
exception, native signal, device-lost result or Windows client exit is recorded.
The last client sample reported about 6.84 GiB system memory available. Android's
record establishes a low-memory kill, not Java heap exhaustion, a continuous
leak, the exact native allocation peak or a device reboot.

The same historical Android exit appears in the other exports; it is one event,
not four kills. Binning, alternate CPU and render60 record EVE's Windows child
exit code 0 and completed private-session cleanup. The supervisor misleadingly
calls code 0 unexpected. Their exports alone cannot establish whether the user
quit EVE or it closed unexpectedly, so these are not classified as three crashes.

## Matched warm measurements

CPU/RSS averages use 11 samples between 180 and 235 seconds after each latest
station session change. CPU 100% equals one logical CPU. Delivery averages span
the entire display connection, including different startup/login lengths; they
are not engine FPS and are not controlled proof of a flag's speedup.

| Run | Requested settings | Lifetime updates/s | Raw MB/s | Warm client CPU | Warm display CPU | Warm client RSS |
|---|---|---:|---:|---:|---:|---:|
| baseline | render30/display30; no flags | 14.24 | 37.08 | 215.4% | 24.7% | 2997 MiB |
| binning | render30/display30; `TU_DEBUG=nocb` | 17.40 | 49.16 | 207.1% | 24.5% | 2982 MiB |
| alt | render30/display30; `FEX_HOSTFEATURES=disablelrcpc2` | 16.54 | 47.73 | 203.3% | 29.5% | 2983 MiB |
| 60 | render60/display30; no flags | 14.77 | 38.35 | 203.4% | 30.8% | 2996 MiB |

Memory approaches 3 GiB and plateaus in later experiment samples; no continuing
leak is demonstrated by these five-to-six-minute runs. Warm shader-worker CPU
is zero. DXVK completion threads wait in `adreno_drawctxt_wait` in 6–7 of 11
warm samples per run, supporting GPU completion/copy/readback pressure without
distinguishing game rendering from capture. Android decode/bitmap publication
averages 2.9–3.1 ms/update, and input queue delay averages 0.28–0.40 ms with no
rejected inputs. Static camera does not mean static pixels: 70–78% of a full
framebuffer changes per update due to animation/HUD.

Thermal status at each export is 0, with power saving off. The old exports lack
live temperature, clock and thermal-status histories. The observed temperature
rise is credible; thermal throttling is not established. Requested Turnip/FEX
flags retain `nativeEffectVerified=false`: environment assignments do not prove
native implementation effect. Binning has the highest delivered-update average,
followed by alternate CPU, but neither is promoted as a confirmed FPS winner.

## Resulting 0.1.14 changes

- Treat a session-bound, observed Windows child exit 0 as normal closure, retain
  startup/nonzero failures and clean only the owned private client/display.
- Respond asynchronously to exactly Android RUNNING_CRITICAL with an orderly
  client stop; preserve the server and ignore UI-hidden/background trim levels.
  Keep bounded Android memory, thermal and critical-pressure evidence.
- Keep the original driver default; offer a separately built, A740-gated Mesa
  26.0.0 variant with a minimal backport of upstream commit
  `23f94c692cb1d41a2193a80fa531922d386e8d5d`, A740 `PC_MODE_CNTL` 0x3f → 0x1f1f.
  It requires physical geometry/rendering qualification because related values
  historically caused vertex corruption. No blanket Mesa/Wine/FEX upgrade,
  lower-resolution default, VRAM-report override or unqualified cached-buffer
  option is included.

Exact recipes, patch and provenance accompany the graphics source package.
See TESTING.md for the two-run comparison. Native CI can validate packaging,
driver loading, helper gating and software shader/display regression; it cannot
accept physical A740 performance or geometry correctness.
